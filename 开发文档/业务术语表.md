# 业务术语表

> 版本：v1.0　|　日期：2026-11-19　|　状态：已确认
>
> 用途：统一产品、开发、测试对业务概念的理解。文档中出现的术语以本表为准；中英文代码字段名仅供开发对照。

## 1. 角色与访问控制

| 术语 | 定义 |
|---|---|
| 访客 | 未注册或未登录的用户。受全局路由守卫限制，只能访问登录页和注册页，不能使用任何业务功能。 |
| 注册用户 | 已注册并成功登录的用户，可使用生成、保存、查看、导出等全部功能。 |
| 全局路由守卫 | 所有需登录的页面统一适用的访问控制规则：未登录访问时自动跳转登录页（`login.html`）。 |
| 登录态 | 用户已通过身份验证的状态。本项目以 JWT token 形式存于浏览器 localStorage，作为登录凭证。 |
| 认证 token | 登录成功后发放的 JWT 字符串，请求时放在 `Authorization: Bearer <token>` 头中。有效期 12 小时或 7 天。**注意与「AI token」区分。** |
| 退出登录 | 清除本地 token 并跳转登录页。服务端无会话，不需要接口。 |

## 2. 账号与认证

| 术语 | 定义 |
|---|---|
| 用户名 | 账号标识，3-20 位字母、数字或下划线；全局唯一且**判重不区分大小写**；禁止 `admin`、`root`、`administrator` 三个保留字。 |
| 邮箱 | 账号的第二个登录凭证，标准邮箱格式，全局唯一、判重不区分大小写。**不做邮件验证**，注册即生效。 |
| 密码 | 登录凭证，6-20 位，必须同时包含字母和数字，不允许空格。存储时使用 bcrypt 哈希，禁止明文。 |
| 确认密码 | 注册时第二次输入密码，仅用于前端校验两次输入一致，后端不接收该字段。 |
| 唯一性判重 | 判断用户名/邮箱是否已被占用。不区分大小写（`Tom` 与 `tom` 视为冲突）。前端失焦预检 + 提交时后端兜底。 |
| 保留字 | 系统不允许注册的用户名：`admin`、`root`、`administrator`。 |
| 登录凭证 | 登录页的单个输入框，用户可填用户名或邮箱。内容含 `@` 按邮箱匹配，否则按用户名匹配。 |
| 记住我 | 登录页可选勾选项。勾选后登录态保持 **7 天**；未勾选为会话级（12 小时）。默认不勾选。 |
| 登录锁定 | 同一账号连续登录失败 **5 次**后锁定 **5 分钟**。锁定期内即使密码正确也拒绝登录；登录成功后失败计数清零。 |
| 统一错误提示 | 登录失败时统一提示「用户名或密码错误」，不区分「账号不存在」和「密码错误」，防止账号探测。 |

## 3. 邀请码（注册准入）

| 术语 | 定义 |
|---|---|
| 邀请码 | 注册的强制凭证，用于阻止陌生人注册、防止消耗 AI 接口费用。6-20 位字母或数字，校验不区分大小写，由站长签发。 |
| 签发 | 站长在服务器执行 CLI 命令生成邀请码的行为，不提供网页入口、不接受用户申请。 |
| 邀请码启用/停用 | 邀请码的有效开关。停用后立即失效，已注册用户不受影响。 |
| 邀请码过期 | 邀请码超过 `expires_at` 后失效；未设置过期时间为永久有效。 |
| 使用次数上限 | 一个邀请码最多可被用于注册的次数（`max_uses`）。用满后自动失效。 |
| 邀请来源 | 用户注册时使用的邀请码，记录在 `users.invite_code_id`，仅用于追溯，不参与登录、权限与页面展示。 |
| 邀请码错误 | 邀请码无效时的统一提示，不区分「不存在 / 已停用 / 已过期 / 已用满」四种原因，防止试探有效码。 |

## 4. 计划生成 · 输入条件

| 术语 | 定义 |
|---|---|
| 生成条件 | 生成旅行计划时填写的 11 项出行条件。必填 4 项（目的地、出行天数、人均预算、人数），其余选填。 |
| 出发地 | 行程的起点城市，必填，1-50 字。用于生成去程与返程交通。 |
| 目的地 | 计划的目标城市或地区，自由文本 1-50 字。**支持多城市**（顿号/逗号/斜杠分隔），系统按顺序分配天数并生成城际交通。 |
| 出行天数 | 计划的行程天数，整数 1-15。 |
| 出发日期 | 可选。填写后行程按真实日期组织；未填时按「第 1 天、第 2 天…」组织。 |
| 人均预算 | 每人的预算金额（元），正整数，上限 999999。 |
| 人数 | 出行人数，整数 1-20，**默认 2**。 |
| 兴趣偏好 | 8 个固定标签的多选：历史文化 / 自然风光 / 美食 / 亲子 / 购物 / 夜生活 / 摄影 / 休闲度假。 |
| 行程节奏 | 单选：宽松 / 适中 / 紧凑，默认「适中」。 |
| 交通偏好 | 单选：公共交通为主 / 自驾 / 不限。 |
| 住宿偏好 | 单选：经济型 / 舒适型 / 豪华型 / 不限。 |
| 饮食/特殊需求 | 自由文本，≤200 字，如忌口、带老人小孩等。 |
| 参考攻略 | 用户在生成前主动提交的攻略材料（1-3 条），用于让行程包含真实在地细节。每条为「链接」或「粘贴正文」。 |
| 攻略正文 | 用户粘贴的攻略文字（单条 ≤500 字）。**唯一可靠的内容来源**，直接参与生成。 |
| 攻略链接 | 用户提交的分享链接。**仅作为来源记录与展示，后端不抓取内容**（合规红线）。 |
| 广告过滤 | 对参考攻略内容的清洗流程：规则层（联系方式、营销话术）识别 + LLM 判定广告/软广，剔除后仅保留可用内容。 |
| 合规红线 | 系统不做任何第三方平台内容的自动抓取，参考攻略只能来自用户主动提交。 |

## 5. 计划生成 · 输出内容

| 术语 | 定义 |
|---|---|
| 旅行计划 | AI 根据生成条件产出的一份结构化行程方案（尚未保存时称「生成结果」）。 |
| 生成 | 用户提交生成条件后，后端调用大模型 API 产出完整结构化行程的过程。采用**同步等待**，上限 120 秒。 |
| 同步等待 | 后端拿到完整结果后才返回，前端显示 loading；不使用流式（打字机）输出。 |
| 生成超时 | 生成超过 120 秒未返回，提示「生成超时，请重试」。 |
| 重新生成 | 基于当前条件再次发起一次全新生成。**不自动保存**，结果替换当前展示。 |
| 补充攻略优化 | 在生成结果页或计划详情页补充 1-3 条参考攻略后重新生成一版方案。结果未保存，详情页中可保存为新计划（只增不覆盖）。 |
| 行程概览 | 结果中的总览模块：目的地、天数、整体主题建议、预算汇总。 |
| 交通信息 | 结果中的长途交通模块：去程、返程、城际段。与每日安排里的「交通方式对比」（市内交通）不是一回事。 |
| 去程 / 返程 | 去程 = 出发地 → 首个目的地；返程 = 最后一个目的地 → 出发地。 |
| 城际交通 | 多城市行程中相邻两个城市之间的长途交通（如 哈尔滨→长春）。单城市行程没有此项。 |
| 每日安排 | 按天分块展示的行程主体，每天内分上午/下午/晚间三个**时段块**。 |
| 时段块 | 每日安排的最小组织单位（上午/下午/晚间），含地点/活动、景点提示、交通方式对比、附近美食、餐饮、分项预算、备注。 |
| 景点提示 | 挂在单个景点下的提示信息：是否需预约、建议游览时长、最佳时段、门票区间、装备着装。 |
| 交通方式对比 | 到达某景点的 2-3 种交通选择（如地铁/打车/公交），含时长与费用，并给出推荐方式及理由。 |
| 附近美食 | 景点周边的就餐推荐（2-4 条）：有攻略依据时给门店级信息，否则只给品类建议。 |
| 踩雷帖 | 参考攻略中「避雷/踩坑」类的负向内容，去重后并入对应模块，标注「来自旅行者反馈」。 |
| 预算估算 | 按交通/住宿/餐饮/门票/其他拆分的费用估算及汇总（人均）。 |
| 分项预算 | 单个时段块或单个费用类别对应的金额。 |
| 注意事项 | **目的地通用层**的风险提示：天气、安全、文化习俗等。景点专属提示不在此处，已下沉至每日安排。 |
| 下沉 | 将原本集中展示的信息拆到更细粒度展示：景点专属提示挂到对应景点条目，当日替换建议挂到对应天。 |
| 备选建议 | 分两层：**全局层**（同目的地整体替换方案）+ **当日层**（某天遇排队/闭馆/天气时的替换选项，展示在该天末尾）。 |
| 免责声明 | 固定展示的风险提示：「行程与价格均为 AI 估算，信息非实时，出行前请自行核实」；使用过参考攻略时追加攻略说明句。 |
| AI 标题 | 计划标题，保存时由 AI 同步生成（如「昆明 5 日慢游 · 山水与烟火」）。 |
| 摘要 | 列表展示的 1-2 句概括，保存时由 AI 同步生成。 |
| 规则文案 | AI 标题/摘要生成失败时的降级结果：标题=「目的地+N 日游」，摘要=概览首句截断（≤50 字）。 |

## 6. 信息三档口径（防幻觉核心规则）

| 术语 | 定义 |
|---|---|
| 三档口径 | 按幻觉风险对 AI 输出信息分级的规则，决定「无攻略依据时能否给出、是否标注」。三档为：定性建议、实时性事实、门店级推荐。 |
| 定性建议 | 第一档。游览顺序、交通方式优劣对比、美食品类等主观性建议，**始终可给**，不依赖参考攻略。 |
| 实时性事实 | 第二档。门票区间、开放时间、具体线路、票价等。可给，但无攻略依据时必须标「以实际为准」。 |
| 门店级推荐 | 第三档。具体店名、招牌菜、距景点距离、酒店品牌。有攻略依据时优先用攻略店铺并标「参考来源」；**无依据时也须给出当地知名店铺并标「以实际为准」**（v1.6 调整），严禁编造不存在的店名。 |
| 品类建议 | 仅当对具体店名确实没有把握时的保底表述（品类 + 街区），不再作为默认输出形式（v1.6）。 |
| 住宿推荐 | 结果页独立模块：2-3 条住宿方案按推荐优先级排序，每条含区域、酒店品牌或类型、档次、价格区间与推荐理由。 |
| 以实际为准 | 标注码 `fact`，表示该实时性信息无攻略依据，出行前需自行核实。 |
| 参考来源 | 标注码 `src`，表示该信息有参考攻略依据，并展示来源链接。 |
| 来自旅行者反馈 | 标注码 `feedback`，表示该内容提炼自用户提交的踩雷帖。 |
| 原创表述 | AI 引用参考攻略时必须用自己的话重写，不复制原文。 |

## 7. 我的旅行计划

| 术语 | 定义 |
|---|---|
| 旅行记录 | 用户保存后的旅行计划，即数据库 `travel_records` 中的一条记录，包含生成条件、AI 内容、攻略使用标记与保存时间。 |
| 我的旅行计划 | 管理已保存计划的页面（原「历史记录查看」），含列表、搜索、详情、删除、复制。 |
| 保存 | 将当前生成结果落库的动作。**只增不覆盖**：每次保存都产生一条新记录，已保存记录不可修改。 |
| 只增不覆盖 | 保存的数据模型约束：不做更新操作，重复保存 = 多条记录。 |
| 列表排序 | 固定按保存时间倒序，不提供切换。 |
| 分页 | 每页 10 条，数字页码 + 上/下页 + 总条数。 |
| 搜索 | 单个关键词模糊匹配「计划标题 + 目的地」；关键词为空时展示全部。 |
| 计划详情 | 展示某条已保存计划的完整内容（结构同生成结果页）并显示保存时间。内容为保存时的快照，不做 AI 重新生成。 |
| 硬删除 | 确认后物理删除数据，不进回收站、不可恢复。删除前需二次确认。 |
| 二次确认 | 删除前弹出「确定删除该计划吗？删除后不可恢复」的确认框。 |
| 复制/分享 | 将「行程概览 + 每日安排」整理为纯文本写入剪贴板，末尾附免责声明。**不含用户名、邮箱等隐私**。 |
| 空状态 | 无任何计划时的引导页：「暂无旅行计划，去生成你的第一个行程吧」。 |
| 越权访问 | 用户尝试访问、删除、导出他人的计划。后端按登录用户过滤，统一返回 403「无权访问」。 |
| 数据归属 | 每条计划归属于创建它的用户，所有读写必须校验归属。 |

## 8. PDF 导出

| 术语 | 定义 |
|---|---|
| PDF 导出 | 将已保存的计划导出为可视化 PDF 文档的功能。独立模块、独立接口，不影响浏览与查看。 |
| 导出入口 | 两处：生成结果页**保存成功后出现**按钮；计划详情页**始终显示**按钮。 |
| 十一部分 | PDF 的固定结构：封面、行前准备清单、交通信息、行程总览、住宿与市内交通、每日安排、景点速查表、费用参考、注意事项、备选建议、免责声明。 |
| 复用部分 | 直接取自已保存计划数据的 7 个部分：封面、行程总览、每日安排、费用参考、注意事项、备选建议、免责声明。 |
| 增量内容 | 导出前额外调用一次 LLM 生成的 4 个部分：行前准备清单、交通信息、住宿与市内交通、景点速查表。 |
| 内部预算 | 增量内容 LLM 调用的时间上限 **20 秒**（小于导出总超时 30 秒），到期即切断并降级，确保降级先于全局超时发生。 |
| 配图 | 封面 1 张 + 每日 1 张（最多 16 张），来自免费授权图库，每张标注「图片来源：XX · 仅供参考」。 |
| 无图版式 | 配图全部失败时的降级版式：纯排版、无图片，**导出仍成功**。 |
| 静默降级 | 非核心环节失败时不向用户报错、流程继续执行的策略。适用于：配图失败、增量内容失败、参考攻略全部无效。 |
| 不存档 | PDF 每次即时生成、即时下载，服务端不保留历史文件，无下载列表。 |

## 9. 系统与通用

| 术语 | 定义 |
|---|---|
| 生成结果页 | 生成成功后展示行程的页面。未保存时无「导出 PDF」按钮；重新生成后按钮隐藏，重新保存后再次出现。 |
| 统一响应格式 | 所有 JSON 接口的返回结构：`{code, message, data}`。`code=0` 表示成功，失败时等于 HTTP 状态码。 |
| 降级 | 某个非关键环节失败时改用规则或简化方案，保证主流程可用。降级一律不向用户报错（除非主流程失败）。 |
| 防重复提交 | 提交中禁用按钮并显示 loading，防止用户重复点击产生重复请求。 |
| 最小化收集 | 隐私原则：只收集出行条件与偏好，不收集姓名、手机号、证件号等个人信息。 |
| AI token | 大模型按输入输出文本计费的单位（消耗 API 费用）。**注意与「认证 token」区分。** |
| 提示词（Prompt） | 发送给大模型的指令文本，本项目要求中文输出、固定 JSON 结构、遵守三档口径。 |
| JSON mode | DeepSeek API 的结构化输出模式，保证返回可解析的 JSON。 |

## 10. 易混淆术语对照

| 易混淆 | 区别 |
|---|---|
| **旅行计划** vs **旅行记录** | 旅行计划是 AI 生成的结果（未保存则不存在于数据库）；旅行记录是**已保存**的计划，对应数据库中的一条 `travel_records`。 |
| **认证 token** vs **AI token** | 前者是登录凭证（JWT 字符串）；后者是大模型计费单位。文档中一律写全称，不简称「token」。 |
| **注意事项** vs **景点提示** | 注意事项只保留目的地通用层（天气、安全、习俗）；景点相关的预约、门票、时长等属于「景点提示」，挂在对应景点条目下。 |
| **备选建议（全局）** vs **当日备选** | 全局层是同目的地整体替换方案，位于结果页独立模块；当日层是某一天的替换方案，展示在该天末尾。 |
| **参考攻略** vs **参考来源** | 参考攻略是用户**输入**的材料；参考来源是生成结果中**输出**的链接列表，供溯源。 |
| **重新生成** vs **保存** | 重新生成只刷新当前展示，不落库；保存才产生记录。重新生成后导出按钮会隐藏，需重新保存才能导出。 |
| **攻略正文** vs **攻略链接** | 正文粘贴后参与生成；链接只记录来源，不被抓取、不参与内容。 |
| **停用** vs **删除**邀请码 | 停用保留记录，可重新启用，且不破坏用户归属追溯；删除是物理删除，会断开追溯关系（用户字段置空）。 |
| **生成失败** vs **静默降级** | 生成失败是主流程失败，必须提示用户；静默降级是次要环节（配图、增量内容、攻略过滤）失败，用户无感知、流程照常完成。 |
| **保存时间** vs **出游日期** | 保存时间是记录入库时间（列表排序依据）；出游日期是用户填写的出发日期（选填）。 |
| **市内交通** vs **城际交通** | 市内交通指景点之间的短途方式（每日安排里的「交通方式对比」）；城际交通指城市之间的长途段（「交通信息」板块）。 |
| **出发地** vs **出发日期** | 出发地是起点城市（必填）；出发日期是具体出行日期（选填）。 |

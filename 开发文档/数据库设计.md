## 1. 表清单与关系

| # | 表名 | 用途 | 需求来源 |
|---|---|---|---|
| 1 | `users` | 用户账号、登录锁定状态 | 注册 / 登录 |
| 2 | `travel_records` | 已保存的旅行计划（含生成条件 + 计划内容） | 计划生成 3.5 / 我的旅行计划 |
| 3 | `invite_codes` | 注册邀请码及使用次数 | 注册 §2.5 / 邀请码管理 |

关系：

```
users 1 ────< travel_records      （user_id 外键，一个用户多条计划，级联删除）
invite_codes 1 ────< users        （invite_code_id 外键，一个码可被多个用户使用；删码置空）
```

> **本期不需要第 4 张表**。PDF 导出不存档（PDF PRD §7）、分享走剪贴板不落库（列表 PRD §3.5）、JWT 无状态不需要会话表。详见 §9「扩展预留」。

## 2. 全局约定

| 项 | 约定 |
|---|---|
| 命名 | 表名、字段名全部 snake_case（与接口 JSON 一致） |
| 主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` |
| 时间存储 | **统一存 UTC**，类型 `DATETIME`；接口返回 ISO 8601（如 `2026-11-19T07:42:00Z`），由前端转本地时间显示 |
| 时间生成 | 应用层用 `datetime.now(timezone.utc)` 写入，不用 SQLite 的 `CURRENT_TIMESTAMP`（后者不带时区标识） |
| 布尔 | `BOOLEAN`（SQLite 底层 INTEGER，0/1） |
| 枚举 | 直接存中文定值（如「适中」），项目为单语言应用，避免前后端映射成本 |
| 列表/对象 | 存 `TEXT` 类型的 JSON 字符串（SQLAlchemy `JSON` 类型），读取时反序列化 |
| 删除策略 | 计划为**硬删除**（PRD 明确）；不做软删除、不做回收站 |
| 外键 | 建表时 `PRAGMA foreign_keys=ON`（SQLAlchemy 需在 connect 事件中开启，SQLite 默认关闭） |
| 字符集 | UTF-8（SQLite 默认） |

## 3. users 表

| 字段 | 类型 | 约束 | 描述 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 用户 ID |
| `username` | VARCHAR(20) | NOT NULL，**唯一（不区分大小写）** | 用户名，3-20 位字母/数字/下划线，禁止 `admin`/`root`/`administrator` |
| `email` | VARCHAR(100) | NOT NULL，**唯一（不区分大小写）** | 邮箱，登录可用邮箱 |
| `password_hash` | VARCHAR(100) | NOT NULL | bcrypt 哈希（60 字符，留余量）；**禁止明文** |
| `failed_login_count` | INTEGER | NOT NULL DEFAULT 0 | 连续登录失败次数，登录成功清零 |
| `locked_until` | DATETIME | NULL | 锁定到期时间；`failed_login_count=5` 时写入 now+5min，到期后计数归零 |
| `created_at` | DATETIME | NOT NULL | 注册时间 |
| `last_login_at` | DATETIME | NULL | 最近登录时间（运维排查用，非必填） |
| `invite_code_id` | INTEGER | NULL，FK → invite_codes.id **ON DELETE SET NULL** | 注册时使用的邀请码（v1.1 新增）；仅作溯源，不参与登录等逻辑；历史/开发用户可为空 |

索引：

```sql
CREATE UNIQUE INDEX uk_users_username ON users(username COLLATE NOCASE);
CREATE UNIQUE INDEX uk_users_email    ON users(email    COLLATE NOCASE);
CREATE INDEX        idx_users_invite  ON users(invite_code_id);
```

> **大小写不敏感的唯一性怎么实现**：注册 PRD §2.1 要求「Tom 与 tom 视为冲突」，SQLite 的普通唯一索引是大小写敏感的。必须用 `COLLATE NOCASE` 的表达式索引（用户名只含 ASCII 字母数字下划线，NOCASE 完全够用，不涉及中文）。
> SQLAlchemy 写法：`Index('uk_users_username', text('username COLLATE NOCASE'), unique=True)`。

登录锁定逻辑（对应登录 PRD §5）：

- 登录失败：`failed_login_count += 1`；若达到 5，写入 `locked_until = now + 5min`
- 登录时先判断 `locked_until > now` → 直接返回「尝试次数过多，请 5 分钟后再试」（**即使密码正确也拒绝**）
- `locked_until` 已过期 → 重置 `failed_login_count = 0`、`locked_until = NULL`
- 登录成功：`failed_login_count = 0`、`locked_until = NULL`、`last_login_at = now`

## 4. travel_records 表

保存对象 = **生成条件 + AI 生成内容 + 攻略使用标记**（生成 PRD §3.5）。**只增不覆盖**：每次保存插入新行，本表不做 UPDATE（`updated_at` 故不设）。

| 字段 | 类型 | 约束 | 描述 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 计划 ID |
| `user_id` | INTEGER | NOT NULL，FK → users.id ON DELETE CASCADE | 归属用户；**所有查询必须带此条件**（数据归属约束） |
| `title` | VARCHAR(100) | NOT NULL | 计划标题；保存时 AI 同步生成，失败降级为「目的地+天数+日游」 |
| `summary` | VARCHAR(100) | NOT NULL | 列表摘要（1-2 句）；AI 失败降级为概览首句截断（≤50 字） |
| `departure` | VARCHAR(50) | NULL | 出发地（生成条件，v1.7 新增）；历史记录可为空 |
| `destination` | VARCHAR(50) | NOT NULL | 目的地（生成条件）；支持多城市（顿号/逗号分隔） |
| `days` | INTEGER | NOT NULL，CHECK 1-15 | 出行天数 |
| `start_date` | DATE | NULL | 出发日期（选填）；为空时行程按「第 1 天、第 2 天…」 |
| `people` | INTEGER | NOT NULL，CHECK 1-20 | 人数 |
| `budget_per_person` | INTEGER | NOT NULL，CHECK ≥1 | 人均预算（元/人） |
| `interest_tags` | TEXT (JSON) | NULL | 兴趣偏好，如 `["自然风光","美食","摄影"]` |
| `pace` | VARCHAR(10) | NULL | 行程节奏：宽松 / 适中 / 紧凑（未选时存「适中」） |
| `transport_pref` | VARCHAR(20) | NULL | 交通偏好：公共交通为主 / 自驾 / 不限 |
| `hotel_pref` | VARCHAR(20) | NULL | 住宿偏好：经济型 / 舒适型 / 豪华型 / 不限 |
| `special_needs` | VARCHAR(200) | NULL | 饮食/特殊需求自由文本 |
| `used_guide` | BOOLEAN | NOT NULL DEFAULT 0 | 本次生成是否使用了参考攻略（决定详情/PDF 免责声明是否追加攻略句） |
| `guide_sources` | TEXT (JSON) | NULL | 参考来源列表（仅来源类型与链接，**不存粘贴正文**），结构见 §6.2 |
| `plan_content` | TEXT (JSON) | NOT NULL | AI 生成的完整计划内容，结构见 §6.1 |
| `created_at` | DATETIME | NOT NULL | 保存时间（列表排序依据） |

索引：

```sql
CREATE INDEX idx_travel_records_user_time ON travel_records(user_id, created_at DESC);
```

> 列表查询是「按 user_id 过滤 + created_at 倒序 + 分页」，该复合索引一次覆盖。搜索（标题/目的地 LIKE 模糊匹配）在 SQLite 中无法走索引，但本项目数据量小（单用户最多几十条），可接受。

约束说明：

- `CHECK` 约束在 SQLite 中需建表时声明，同时后端 Pydantic 层也要校验（双重保险，接口层校验给用户可读文案）
- 硬删除：`DELETE FROM travel_records WHERE id=? AND user_id=?`，**必须同时带 user_id**，防止越权删除

## 5. invite_codes 表

完整字段定义与操作流程见《开发文档/邀请码管理.md》，此处为数据库视角的正式定义。

| 字段 | 类型 | 约束 | 描述 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 主键 |
| `code` | VARCHAR(20) | NOT NULL UNIQUE | 邀请码，**统一存大写**；校验时先 `upper()` 再比对（实现不区分大小写） |
| `note` | VARCHAR(50) | NULL | 备注（发给谁 / 用途） |
| `max_uses` | INTEGER | NOT NULL DEFAULT 1，CHECK ≥1 | 最大可用次数 |
| `used_count` | INTEGER | NOT NULL DEFAULT 0，CHECK ≥0 | 已用次数 |
| `expires_at` | DATETIME | NULL | 过期时间；NULL = 永不过期 |
| `enabled` | BOOLEAN | NOT NULL DEFAULT 1 | 是否启用（停用后立即失效） |
| `created_at` | DATETIME | NOT NULL | 签发时间 |

注册时校验顺序（对应注册 PRD §2.5）：

1. `code = input.upper()` 查记录，不存在 → 无效
2. `enabled = 1` 否则无效
3. `expires_at IS NULL OR expires_at > now` 否则无效
4. `used_count < max_uses` 否则无效
5. 全部通过 → **在同一事务内**创建用户 + `used_count += 1`（防止并发超发）

任一不满足统一返回 400「邀请码错误」，不区分原因。

**标注码值统一定义**（三档口径）：

### 6.2 guide_sources

```jsonc
[
  { "type": "link", "url": "https://example.com/post", "label": "分享链接" },
  { "type": "text", "url": null, "label": "用户粘贴的攻略正文" }
]
```

- **只存来源元信息，不存粘贴的正文原文**：正文仅用于本次生成，留存无必要且涉及隐私与存储成本
- 与 `plan_content.sources` 内容一致，独立成列是为了支持「按是否用攻略」的筛选与统计，避免解析大 JSON

## 7. 建表 SQL（SQLite 完整版）

> **建表顺序**：`invite_codes` 必须最先创建（users 引用它），`users` 次之（travel_records 引用它）。

```sql
PRAGMA foreign_keys = ON;

-- 邀请码表（必须最先建）
CREATE TABLE invite_codes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    code       VARCHAR(20)  NOT NULL UNIQUE,
    note       VARCHAR(50),
    max_uses   INTEGER      NOT NULL DEFAULT 1 CHECK (max_uses >= 1),
    used_count INTEGER      NOT NULL DEFAULT 0 CHECK (used_count >= 0),
    expires_at DATETIME,
    enabled    BOOLEAN      NOT NULL DEFAULT 1,
    created_at DATETIME     NOT NULL
);

-- 用户表
CREATE TABLE users (
    id                 INTEGER PRIMARY KEY AUTOINCREMENT,
    username           VARCHAR(20)  NOT NULL,
    email              VARCHAR(100) NOT NULL,
    password_hash      VARCHAR(100) NOT NULL,
    failed_login_count INTEGER      NOT NULL DEFAULT 0,
    locked_until       DATETIME,
    created_at         DATETIME     NOT NULL,
    last_login_at      DATETIME,
    invite_code_id     INTEGER      REFERENCES invite_codes(id) ON DELETE SET NULL
);
CREATE UNIQUE INDEX uk_users_username ON users(username COLLATE NOCASE);
CREATE UNIQUE INDEX uk_users_email    ON users(email    COLLATE NOCASE);
CREATE INDEX        idx_users_invite  ON users(invite_code_id);

-- 旅行计划记录表
CREATE TABLE travel_records (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id           INTEGER      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title             VARCHAR(100) NOT NULL,
    summary           VARCHAR(100) NOT NULL,
    departure         VARCHAR(50),
    destination       VARCHAR(50)  NOT NULL,
    days              INTEGER      NOT NULL CHECK (days BETWEEN 1 AND 15),
    start_date        DATE,
    people            INTEGER      NOT NULL CHECK (people BETWEEN 1 AND 20),
    budget_per_person INTEGER      NOT NULL CHECK (budget_per_person >= 1),
    interest_tags     TEXT,
    pace              VARCHAR(10),
    transport_pref    VARCHAR(20),
    hotel_pref        VARCHAR(20),
    special_needs     VARCHAR(200),
    used_guide        BOOLEAN      NOT NULL DEFAULT 0,
    guide_sources     TEXT,
    plan_content      TEXT         NOT NULL,
    created_at        DATETIME     NOT NULL
);
CREATE INDEX idx_travel_records_user_time ON travel_records(user_id, created_at DESC);
```

## 8. 数据归属与安全约束（最高优先级）

对应 `CLAUDE.md`「接口约定」第 3 条：

1. **所有 travel_records 的读写必须由后端从 JWT 解析出 user_id 后拼接条件**，禁止相信前端传入的 user_id
2. 详情 / 删除 / 导出：`WHERE id = ? AND user_id = ?`，影响行数为 0 时返回 403「无权访问」
3. 列表 / 搜索 / 分页：`WHERE user_id = ?` 基础上叠加条件
4. 用户删除时计划级联删除（`ON DELETE CASCADE`），但本期无删除用户功能
5. `users.invite_code_id` 与 `invite_codes` 建外键（v1.1 用户拍板）：用于**追溯邀请来源**，即「某码被谁用了」。该字段只作溯源，不参与登录、权限、展示等任何业务逻辑；删除邀请码时置空（SET NULL），不影响用户登录
